# S69: gaps and contradictions in the written description (phase 1)

This list is what the third independent implementation of the model needed beyond the written description (`MODEL_SPEC.md`, `ODD.md`, `TESTBED_SPEC.md` and `reference/KEYS.md`, in the S69 packet built at engine commit 26d9b47). Each item says what the description says or leaves out, and what the code excerpt settled. Line numbers are those of `code/main-row-code-full.js` in the packet, with the engine file and line the excerpt names for that piece in brackets.

**How the excerpt was used.** The brief asks for the program to be written from the description first, with the code opened only for questions the description leaves open. In practice the description was enough for the shape of every mechanism and for the random draws. It was not enough to reproduce the numbers to the last digit: for that, almost every part needed some detail from the code (an order of operations, a default, a tie rule, a table). So the program follows the code excerpt closely, part by part, and this list records where the description fell short. The program agrees with the reference to rounding (`REPORT.md`). That shows that the excerpt and the program do the same thing, and that the description matches both in every place it is specific. It does not show that someone could write the model from the description alone. Items 1-9 would stop such a person; the others would cost them digits.

## A. Contradictions (the description says one thing, the code another)

1. **The year-0 labour-force draw with yearly flows.** MODEL_SPEC 14.15: "With `fl`, the year-0 draw uses the fitted stock (by sex where adults have one)." The code uses the fitted stock only for adults who have an age. Without ageing (the candidate main row has none), the year-0 draw uses S61's shares by household type (`CFG.LF_SHARES`). Settled by `lfDraw`, line 1334 [index.html 4264]. Either the text or the code should change. With ageing off, the text promises a draw the code does not make.
2. **The order of set-up in 14.0.** 14.0 says the order at initialisation is "the outside-the-labour-force draw (14.4), the tail (14.8), the asset-class split and owners' draw (14.6)". In the code the tail is drawn inside the households' SCF wealth (`hhScfWealth`, line 1603 [4485]), before the labour-force draw (`lfInit`, line 1342 [4270]). The asset-class split and the owners' draw happen when year 0 starts (`rtInit`, line 1184 [4151]), not at initialisation. Each part has its own stream, so no number depends on this; the text should just be corrected.
3. **One supply path for every row.** 13.2 (`sp`) says every row of a seed gets the same path "whatever the order of rows". In the code each row builds its own supply-path run (`tbBaseS`, line 4101 [6846]) with the row's economy-wide settings. The candidate main row's run keeps the row's pathway setting (the octave wage raise off) and `noDamp`, so it is a different run from the no-programme row's. Here the two give identical paths (the settings they differ in do nothing without a programme), so the statement holds for this pair. It is not true by construction.

## B. Gaps that stop an implementation

4. **The US-data wage reading (`lt: {s: 'all', m: 'all'}`).** 14.0 names "CPS earnings" and TESTBED_SPEC 7.1 gives the option a plain name; neither gives the rule. In the code each adult's wage becomes `exp(ln(60,000 / (12 × 100.52)) + 0.737 z)`, where `z = (ln wage − 3.5)/0.5` is the wage draw's own normal score. The median and spread are `CFG.CPS_EARN.all`; the wealth and risk readings are off. This is applied to the latent adults before anything else reads a wage. Settled by `latentAdjust`, line 1492 [4385], and the `lt` line of `tbStudy`, line 4626 [7469 ff.]. Without it every wage, occupation and household wealth differs.
5. **Tables missing from the configuration file.** The brief says `main-row-config.json` holds every setting. It does not hold the asset-class tables (`RT_GROUPS`, `RT_GROUPS_O`, `RT_GROUPS_N`, `RT_EDGES`, `RT_YLD`, `RT_SOLE`, `RT_NG`, `RT_RG`, `RT_DEFAULTS`, `CR_DEFAULTS`), the tail's cut-offs (`WT_CUTS`) or today's debt (`GV_US`): they are top-level values of the engine that the capture did not list. They were read from the excerpt, lines 1045-1100 and 1236-1258 [4078-4100, 4216-4218] and the S72 block, and are kept in `code_tables.json` (written by `dump_tables.js`, which reads the excerpt's values and calls no engine function).
6. **Stress's configuration lists two runs, not four.** For Reference and Adverse the file captures four calls (each row's supply-path run, then the row). For Stress it captures only the two rows. The supply-path runs' settings were rebuilt by `tbBaseS`'s rule (line 4101 [6846]: the row's options without the programme-only ones, `SP_PROG_OPTS`, and the programme's switches at their defaults). In Reference and Adverse that rule gives exactly the captured settings (`s69_check_capture.py`).
7. **The take-up hash.** Appendix C, item 22 gives the hash's inputs (seed + 700001, the head's index, 0, slot 31 or 32) but not the hash: murmur3's finaliser over the mixed integers, `((h >>> 0) + 0.5)/2^32`. Settled by `hlU`, line 3019 [index.html 5663 ff.].
8. **The reporting keys.** KEYS.md says the code is the definition of each part's own keys. About 700 of the roughly 960 keys are defined only there: distribution measures, the tail's measures, asset classes and the creditor side, risk, spells, households, the price rule's record, money flows, within-year costs, the government account, the financing identity, bargaining, labour-force flows. Each was ported from its function (`dmYear`/`dmRes` [7343-7380], `wtRep` [4239], `rtRep` [4162], `tbRiskRes` [5088 ff.], `tbRepSpells` [5068], `hhRepYear`/`hhRepRes2` [4673-4705], `prStep`/`prRes`, `mfYear`/`mfRes`, `wyYear`/`wyRes`, `gvStep`/`gvRes`, `finStep`/`finRes`, `bgAcc`/`bgRes`, `lfAcc`/`lfFlowRes`).
9. **Which helper runs when.** Section 5 gives the order of events but not where the round-2 parts sit inside it. Settled by `runYear`, line 3236 [5992], and `tbRunCore`, line 4161 [6895]. Examples: the open-access share grows before the density test and before PTF leavers; the creditor totals are taken at the first adult's turn; the safety net is set before PTH's books and joining; the participation margin acts after the bargained raise and the hours response.

## C. Details the description leaves loose (each moves digits)

10. **The weighted tail (14.8).** (a) The tail's draws are taken for each household type in the order couples with children, couples without, single parents, singles, `m` draws each, even for a type with no households. (b) The lower households' wealth follows the type's table up to its last point (99.5%); beyond it the code joins the table to the cut-off by a geometric bridge, `q × (u/q)^((P − 0.995)/(pc − 0.995))`. The description says only "the table's wealth at `min(p × c, 1 − pi_t)` (at most `u`)". (c) Households are ranked by their place `p`, ties by index. (d) Each adult's place in the population (`_wtP`, read by the top interest rates) is by weight, at the middle of its own weight. Settled by `wtTable`, `wtAssign`, `wtRank`, lines 1271-1287 [4224-4236].
11. **Ties in the SCF ranks.** Households are ranked on their summed wages and on their summed wealth draws; equal values keep household order (a stable sort). Settled by `hhScfWealth`, line 1603 [4485].
12. **The refundable Child Tax Credit (12.4).** The description gives the smaller of $1,700 a child, 15% of earnings above $2,500, and the credit left after income tax. The code first phases the $2,200 credit out above $200,000 ($400,000 joint) at 5%, then takes the credit left after income tax (standard deduction and 2025 brackets, `CFG.SN_TAX`). Settled by `snBen` and `snIncTax`, lines 3104-3118 [5884-5895]. It never binds at these incomes; it is in the program for completeness.
13. **Asset classes (14.6).** (a) The group is read from the household's net worth in year-0 dollars at the start of year 0 (`Wh/P`). (b) An adult whose gross assets would be negative (`G < 0`, net worth of the other sign from the household's) holds everything in one class: nominal assets if positive, floating debt if negative. They have no group, no capital income, and the creditor side reads the all-groups bond share (`tAll`). (c) Capital income is computed on the holdings after the year's revaluation and paid in that year, from year 0 (when it is computed on the opening split). (d) The top 0.1% and 0.01% interest-rate ratios are 1.52/0.91 and 3.79/0.91 (`RT_NG`), read from the adult's place `_wtP` ≥ 0.999 or ≥ 0.9999. (e) Business owners: one draw per household, made when its first adult is seen, from `RT_OWN` at the household's group. Settled by `rtOpen`, `rtCap`, `rtInit`, `rtAdult`, lines 1154-1197 [4133-4161].
14. **The creditor side (14.7).** The year's totals are taken on a copy of each adult's balances with last year's saving placed. The year's inflation `π` is read from the first adult's price levels. Totals are weighted and divided by the total weight, with the year-0 price level over this year's as the deflator. The book loss counts deposits too (`book = h × π × (kb + kd)`) although under 'pass' depositors are not charged. Settled by `crYear` and `crRates`, lines 1135-1150 [4118-4132].
15. **The borrowing limit (14.5).** What the household can draw is `max(0, start-of-year wealth + limit × price level)`, so negative savings use up the limit first. For a couple it is the partners' wealth together. Settled by `drExtra`, line 1429 [4332], and `hhPool`, line 1637 [4513].
16. **A couple's year end (6.13).** The order is: the spending share on the pooled surplus (split equally), then the income-graded cut with the borrowing limit, then wealth averaged between the partners, then the price module's unmet need, then poverty status from the household's totals, then the floor. Settled by `hhPool`, line 1637 [4513].
17. **PTH's books (12.2, 13.2 `pthb`).** Books open for every adult in PTH after households are formed, so a couple in community housing holds two homes, one per adult, each with its own books. A leaver's home passes to the next adult on the waiting list in the order of their PTH draw; a partner's place on that list is kept. Settled by `pthbInit` and `pthbYear`, lines 2441-2452 [5198-5209].
18. **PTH's equity contribution under `hb`.** With `fx.hb` the home's price and the trust's receipt use the basket's housing cost. The quarter of the PTH saving routed to Acre Equity is still measured at the BLEI daily cost (`dcA`). Settled by `runYear`'s PTH block, line 3745 [runYear, index.html 5992 ff.]. Section 11 says the base is the BLEI daily cost; 13.2 does not say that `hb` leaves it so.
19. **PTF by sector's share of utilities.** `PTFS_UTIL = 487.685/(3,326.284 + 487.685)`, as 12.3 says (12.78%), but the code's figure has more digits than the text's 487.7/3,814.0; the program uses the code's.
20. **The participation margin's dollars (14.15).** `L` is the income effect's programme dollars, times the share of the year at work. `E` is this year's earnings after the raise and displacement, less the income effect's other part (the safety net's dollars and the in-kind cuts, at ρ). Settled by the `lfPM` call in `runYear`, line 3604 [runYear, index.html 5992 ff.], and `lfPM`, line 1403 [4314].
21. **Default values where a quantity is missing.** For example: the project pool's mean rate is 1 when no participant has weight; the price module's demand is 1 with no adults; a SNAP household of more than eight people takes $218 a month for each person beyond eight. None of these is reached in these runs; they are in the program as the code has them.

## D. What the check found in the engine (not gaps in the text)

22. **"Worked this year" is decided by rounding when the whole of the year's earnings goes to the income effect.** Under the participation margin, a worker who stays loses `(1 − pm) × min(L, E)/(1 − q)`. When `L ≥ E` that is exactly `E`, so the year's earnings are zero in exact arithmetic. In floating point the subtraction leaves about ±10⁻¹⁰ dollars, and the sign of that remainder decides whether the year counts as worked: in the share of adult-years with earnings (`emp`, `lfPart`), in `zero`, in next year's EITC take-up count (`snEitc`), and in the working adults' median wage (`pwageR_t`). Where this program and the engine round the last digit differently, those keys differ by one adult-year (0.01 points). Usually every dollar figure agrees. It is not always cosmetic: an adult-year with 10⁻¹⁰ dollars of earnings counts as earning for next year's EITC, so the household's marginal rate next year includes the credit's phase-in and its hours move. In Reference main-row seed 246 that moved the price level at year 20 by 5 parts in a million (653.834 against 653.837) and the cost per adult by 2 parts in 100 million. A fix belongs behind a switch: treat earnings below 10⁻⁹ dollars as zero. Proposed for the design freeze's list, not applied here.
23. **The creditor ledger's gap (`crGap`) is rounding noise of about 10⁻¹¹ to 10⁻¹⁰** in both programs, as the description says ("0 to rounding"). It is the difference of sums of thousands of dollars, so it cannot be compared digit for digit. `s69_compare.py` compares it against the size of the ledger (`crRel`).
24. **Ties at the borrowing limit decide the weighted distribution measures.** Households whose spending the borrowing limit cuts end the year at minus the limit: in exact arithmetic exactly −$2,500 in Reference. In floating point they end within about 10⁻¹¹ of it, on either side. In seed 5 of the no-programme run, 43 adults sit there at year 20 (24 exactly, 19 within 10⁻¹¹), from two household types with different weights. The weighted fifths of wealth (`dmMob…`) and some low weighted percentiles (`dmWp10…`, `dmWp20E`, the median debt `dmDmS`) sort adults by wealth, so the order of these near-ties, and so which adult falls on which side of a fifth's edge, is set by the last binary digit. This program and the engine round those digits differently in 4 to 37 of 500 seeds, and those keys then differ (by up to one point in a mobility share and up to about $90 in a percentile). The means over 500 seeds agree within two standard errors. The fix belongs behind a switch: rank on wealth rounded to the cent, ties broken by index. Proposed for the design freeze's list, not applied here.
25. **Where the last-digit differences start.** The two programs do the same arithmetic in the same order. They round differently only where a mathematical function is called: the power, exponential and logarithm functions of JavaScript (V8) and of Python (the C library) do not always agree in the last binary digit. For example, Adverse's outside price index at year 12 is 1.02¹²: Python gives 1.2682417945625455, the correctly rounded value, and the engine gives 1.2682417945625457, one binary digit above it, in every seed (`plv_12`). Such one-digit differences are invisible in every measure (one part in 10¹⁶) except where a rule compares two quantities that are equal in exact arithmetic (items 22-24).
